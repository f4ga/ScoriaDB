## Категории (все — CRIT)

| Область | Описание |
|---------|----------|
| **Потеря данных / durability** | Нарушение гарантий сохранности данных при сбоях, shutdown, крашах. |
| **Гонки и use-after-free** | Некорректная работа в многопоточном окружении, SIGBUS, паника. |
| **MVCC и изоляция** | Нарушение Snapshot Isolation, потеря версий, неверные чтения. |
| **Производительность и масштабирование** | Отсутствие линейного масштабирования, contention, падение QPS на многих ядрах. |
| **Аллокации и zero-copy** | Нарушение обещания 0 аллокаций в горячем пути, лишние копирования, GC-нагрузка. |

Все дефекты должны быть исправлены. Некоторые уже помечены как исправленные, но для полноты они включены с комментарием.

# Часть 1. Дефекты (группировка)

## 🔴 ГРУППА A: ПОТЕРЯ ДАННЫХ И DURABILITY

### DEF‑A1 (бывш. DEF‑01) — `unsafeToString` + хранение строки в map → порча ключей

**Файлы:** `internal/engine/cache.go:30-32`, `internal/engine/cache.go:36-40`

**Проблема:**  
`unsafeToString` создаёт строку, разделяющую память с `[]byte`. Эта строка сохраняется как ключ map. Если исходный `[]byte` впоследствии мутируется (что типично для `sync.Pool` или переиспользования буферов), ключ в map изменяется, нарушая `CheckConflict` и Snapshot Isolation.

**Последствия:**  
- Неверные результаты конфликтов транзакций → нарушение SI.  
- Возможна коллизия ключей, потеря записей в кэше.  
- Это критично для корректности транзакций.

**Статус:** ✅ ИСПРАВЛЕНО (август 2026).
`unsafeToString` заменён на явное копирование ключа через `string(append([]byte(nil), key...))`. Исходный `[]byte` больше не разделяет память с ключом map, поэтому мутация буфера не влияет на кэш. Добавлен тест `TestLastCommitCacheKeyStability`.

### DEF‑A2 (бывш. DEF‑03) — таймстампы не восстанавливаются после рестарта

**Файлы:** `internal/engine/lsm.go:128`, `internal/engine/mvcc/mvcc.go:47-57`, `internal/engine/recovery.go`

**Проблема:**  
`LastTS` инициализируется как 1 при каждом старте. `recoverFromWAL` не вызывает `TimestampGenerator.Set(maxCommittedTS)`. После краша новые транзакции получают commitTS, уже использованные ранее → нарушение уникальности и монотонности таймстампов MVCC.

**Последствия:**  
- Версии с одинаковым TS конфликтуют, порядок версий ломается.  
- Snapshot Isolation нарушается.

**Статус:** ✅ ИСПРАВЛЕНО (август 2026).
`recoverFromWAL` теперь собирает максимальный commitTS из всех записей (Put/Delete/Batch) и устанавливает `e.LastTS = max(e.LastTS, maxTS)` после восстановления всех шардов. `LastTS` сохраняется в manifest (`VersionEdit`) и восстанавливается при открытии. Новый TS после рестарта строго больше предыдущего.

### DEF‑A3 (бывш. DEF‑05) — Endianness mismatch в unified mmap

**Файлы:** `internal/engine/unified_mmap.go:161-187` (`WriteEntry`), `internal/engine/unified_mmap.go:214-238` (`ReadEntry`)

**Проблема:**  
`WriteEntry` пишет native‑endian, `ReadEntry` читает BigEndian. На little‑endian платформах (x86, ARM64) восстановление из mmap читает мусор (неверные длины, timestamp).

**Последствия:**  
- Восстановление после краша из unified mmap работает неверно → потеря данных.  
- CRC не сходится или чтение выходит за границы.

**Статус:** ✅ ИСПРАВЛЕНО (август 2026).
`WriteEntry` и `ReadEntry` приведены к единому `binary.BigEndian` порядку для всех много‑байтовых полей (timestamp, keyLen, valueLen). CRC пересчитан order‑independent. Добавлен тест `TestUnifiedMmapEndianness` (запись → переоткрытие → проверка).

### DEF‑A5 (бывш. DEF‑21) — `Manifest.recover()` теряет записи при повреждении

**Файлы:** `internal/engine/manifest.go:93-106`

**Проблема:**
При ошибке декодирования (не `io.EOF`) `recover()` прерывает чтение и возвращает `nil`, игнорируя последующие валидные `VersionEdit`. После краша теряются свежие SSTable.

**Последствия:**
- Потеря данных после восстановления.

**Статус:** ✅ ИСПРАВЛЕНО (август 2026).
`recover()` различает «повреждённая последняя запись» (безопасно игнорируется) и «повреждение в середине» (возвращается ошибка). Хвост‑мусор не теряет валидные записи. Добавлен тест: несколько edits, повреждение середины → `recover` возвращает ошибку.

### DEF‑A6 (бывш. DEF‑27) — Group Commit: `Flush()` не ждёт fsync в Strict Sync

**Файлы:** `internal/engine/wal_group.go`, `internal/engine/wal.go`

**Проблема:**  
В режиме Strict Sync (`syncMode==true`) `Flush()` возвращается сразу после `write(2)`, не дожидаясь `fsync`. Это нарушает обещание «0 потерь».

**Последствия:**  
- При сбое питания после ACK запись теряется → нарушение durability.

**Статус:** ❌ Не исправлено.

**Промпт для исправления:**  
> В `groupCommitWriter.Flush()` добавить условное ожидание завершения `fsync` только при `syncMode == true`. В асинхронном режиме не ждать. Добавить тест: запись с Strict Sync, имитация сбоя, проверка наличия данных после рестарта.

### DEF‑A7 (бывш. DEF‑16) — дупликация `OpBatch` при восстановлении

**Файлы:** `internal/engine/lsm.go`, `internal/engine/recovery.go`

**Проблема:**  
Батч записывается в WAL каждого затронутого шарда целиком. При восстановлении каждый шард реплеит весь батч → дублирование ключей, нарушение инварианта маршрутизации.

**Последствия:**  
- Ключи попадают в несколько шардов → непредсказуемое поведение, сломанная флаш/компакшн.

**Статус:** ❌ Не исправлено.

**Промпт для исправления:**  
> В `recoverFromWAL` при обработке `OpBatch` фильтровать операции: применять только те, у которых `shardIndex(key) == текущий шард`. Это сохраняет атомарность, т.к. батч всё равно записан целиком в каждом WAL. Добавить тест: батч с ключами из разных шардов, восстановление, проверка, что ключи не дублируются.

### DEF‑B4 (бывш. DEF‑14) — невыровненный доступ в `memcpyWordAligned` → SIGBUS на ARM

**Файлы:** `internal/engine/unified_mmap.go:338-350`

**Проблема:**  
`memcpyWordAligned` копирует `uint64` по невыровненным адресам. На ARM это вызывает SIGBUS.

**Последствия:**  
- Крэш на ARM-платформах (заявлена поддержка).

**Статус:** ✅ ИСПРАВЛЕНО (август 2026).
`memcpyWordAligned` удалён и заменён на стандартный `copy()` (runtime `memmove`) для ключей и значений в `WriteEntry`. `copy()` безопасен на всех платформах и обрабатывает выравнивание внутри. Добавлен тест `TestUnifiedMmapUnalignedCopy` с ключами/значениями нечётной длины.

### DEF‑B5 (бывш. DEF‑24) — несогласованное чтение/запись `e.levels`

**Файлы:** `internal/engine/lsm.go`, `internal/engine/flush.go`, `internal/engine/compaction.go`

**Проблема:**  
`e.levels` модифицируется под `Lock`, читается под `RLock`. Формально корректно, но есть риск, что некоторые чтения не используют блокировку должным образом (см. DEF‑B6). Требуется аудит.

**Последствия:**  
- Потенциальная гонка.

**Статус:** ✅ ИСПРАВЛЕНО (август 2026).
Проведён аудит всех обращений к `e.levels`. `NewMergeIterator` теперь снимает снапшот `e.levels` и `e.shards` под `e.mu.RLock` перед построением итератора (ранее читал живые срезы без блокировки). Добавлены комментарии‑инварианты в `lsm.go`: запись только под `Lock`, чтение под `RLock`, читатели копируют слайсы. `-race` чист.

### DEF‑B6 (бывш. DEF‑26) — `decodeMVCCKey` возвращает срез в mmap, который может жить дольше reader

**Файлы:** `internal/engine/sstable/encoding.go:38-52`, `internal/engine/sstable/reader.go`

**Проблема:**  
`decodeMVCCKey` возвращает `userKey := data[4:4+kl]` — срез в mmap. Если этот ключ сохраняется после закрытия SSTable (например, в компакшне), возникает use‑after‑munmap.

**Последствия:**  
- SIGSEGV при компакшне (уже было, частично исправлено копированием в `compactLevel0`, но не везде).

**Статус:** ✅ ИСПРАВЛЕНО (август 2026).
`SSTableIterator.Next()` теперь делает глубокую копию ключа (раньше `decodeMVCCKey` возвращал срез в mmap/пул). Значение уже копировалось. Ключ и значение безопасно живут после перехода к следующему блоку или закрытия reader. Внутри `Lookup` копирование не требуется (срез валиден только на время жизни reader) — это задокументировано.

## 🔴 ГРУППА C: MVCC И СНАПШОТЫ

### DEF‑C1 (бывш. DEF‑07) — SSTable.Lookup возвращает старую версию вместо новой для снапшота

**Файлы:** `internal/engine/sstable/reader.go:578-619`

**Проблема:**  
При поиске в блоке SSTable возвращается первая подходящая версия, а не последняя (с максимальным commitTS <= snapshotTS). Это может отдать старую версию, если есть более свежие, но невидимые для снапшота.

**Последствия:**  
- Нарушение Snapshot Isolation.

**Статус:** ❌ Не исправлено.

**Промпт для исправления:**  
> В цикле сканирования блока запоминать лучшую версию (с максимальным `commitTS <= snapshotTS`), обрабатывать tombstone. Возвращать только после завершения сканирования группы ключа. Добавить тест: SSTable с версиями 10, 20, 30; запрос снапшота 25 должен вернуть 20.

### DEF‑C2 (бывш. DEF‑08) — MVCCIterator сбрасывает живую версию после tombstone

**Файлы:** `internal/engine/mvcc_iterator.go:82-118`

**Проблема:**  
Если у ключа есть старый tombstone и новая живая версия, итератор не возвращает ключ, потому что флаг `hasTombstone` не сбрасывается.

**Последствия:**  
- Потеря данных при сканировании.

**Статус:** ❌ Не исправлено.

**Промпт для исправления:**  
> Сбрасывать `hasTombstone = false` при встрече живой версии. Условие выдачи: если последняя версия живая → возвращать её, независимо от старых tombstone. Добавить тест: версии [tombstone, live] должны возвращать live.

### DEF‑C3 (бывш. DEF‑09) — транзакции не регистрируют снапшоты → компакшн удаляет нужные версии

**Файлы:** `internal/txn/transaction.go`, `internal/engine/snapshot.go`

**Проблема:**  
`Begin` не вызывает `RegisterSnapshot`, поэтому `minActiveSnapshotTS` = 0 → компакшн удаляет версии, нужные активным транзакциям.

**Последствия:**  
- Нарушение Snapshot Isolation (потерянные чтения).

**Статус:** ✅ ИСПРАВЛЕНО (август 2026).
`Begin` и `BeginWithNextTS` теперь вызывают `db.RegisterSnapshot(startTS)` (см. `transaction.go`), `Commit`/`Rollback` вызывают `UnregisterSnapshot`. Добавлен тест `TestTransactionSnapshotRegistration` в `internal/txn/transaction_test.go`. `-race` чист.

### DEF‑C4 (бывш. DEF‑15) — UnregisterSnapshot сбрасывает минимум при наличии других снапшотов

**Файлы:** `internal/engine/snapshot.go:36-41`

**Проблема:**
`UnregisterSnapshot` обнуляет `minActiveSnapshotTS`, если закрывается снапшот с текущим минимумом, не учитывая другие активные.

**Последствия:**
- Компакшн удаляет версии, нужные другим снапшотам.

**Статус:** ✅ ИСПРАВЛЕНО (август 2026).
Введён reference‑counting через `snapshotRegistry` (`internal/engine/snapshot.go`): `counts map[uint64]int` + `min`. При регистрации инкрементируем, при закрытии декрементируем и пересчитываем минимум из оставшихся активных. `GetMinActiveSnapshotTS` читает из регистра. `LSMEngine` больше не хранит единичный `minActiveSnapshotTS`. Добавлен тест `TestSnapshotRefCounting` в `internal/engine/engine_test.go`. Существующие тесты (`TestLSMEngineSnapshot`, `TestRegisterSnapshotEdgeCases`) обновлены под новую семантику. `-race` чист.

**Промпт для исправления:**  
> Ввести reference‑counting для снапшотов: хранить map[TS]count + текущий минимум. При регистрации инкрементировать, при закрытии декрементировать и пересчитывать минимум. Добавить тест: два снапшота (5 и 10), закрыть 5 → минимум должен стать 10.

### DEF‑C5 (бывш. DEF‑18) — компакшн использует `minActiveSnapshotTS`, зафиксированный на старте

**Файлы:** `internal/engine/compaction.go:64`, `internal/engine/compaction.go:130-152`

**Проблема:**  
`compactLevel0` берёт `minActiveSnapshotTS` один раз в начале. Если во время компакшна появляется новый снапшот с меньшим TS, старые версии уже удалены.

**Последствия:**  
- Нарушение изоляции для новых снапшотов.

**Статус:** ❌ Не исправлено.

**Промпт для исправления:**  
> Использовать актуальный минимум на момент записи выходного файла, а не на старте. Либо блокировать появление новых снапшотов с меньшим TS до завершения компакшна (сложно). Рекомендуется пересчитывать минимум на каждой итерации записи.

### DEF‑D6 (НОВЫЙ) — Shard‑per‑core не масштабируется: чтение падает с ростом ядер

**Файлы:** `internal/engine/lsm.go`, `internal/engine/memtable/skiplist.go`, `internal/engine/shard.go`

**Проблема (из бенчмарков):**  
`BenchmarkGetExisting` на 1 ядре → 2.3M оп/с, на 8 ядрах → 0.46M оп/с (падение в 5 раз). Причина: все ключи хешируются в один шард, на 8 ядрах contention на мьютексах (`SkipList.mu`, `LSMEngine.mu`, общий WAL).

**Последствия:**  
- Нарушение заявленного линейного масштабирования.
- При реальных нагрузках с неравномерным распределением ключей возможны аналогичные деградации.

**Статус:** ❌ Не исправлено.

**Промпт для исправления:**  
> 1) Улучшить хеширование (xxHash64 с равномерным распределением).  
> 2) В бенчмарках использовать ≥10000 ключей.  
> 3) Устранить глобальные блокировки в `GetWithTS`/`GetLatestInfo` (копировать указатели под RLock, отпускать).  
> 4) Добавить мониторинг contention через pprof.  
> Это комплексное исправление, планируется для v0.4.0.

### DEF‑D7 (НОВЫЙ) — Аллокации в `decodeStoredValue` для SSTable → лишние копии

**Файлы:** `internal/engine/lsm.go`, `internal/engine/sstable/reader.go`

**Проблема:**  
В `decodeStoredValue` при `fromSSTable=true` делается `make([]byte, len(stored))` и копирование. Это добавляет аллокацию на каждый GET из SSTable.

**Последствия:**  
- Увеличение нагрузки на GC, рост задержки.
- Противоречит принципу zero‑allocation.

**Статус:** ❌ Не исправлено.

**Промпт для исправления:**  
> Для значений из SSTable, которые не модифицируются, возвращать срез непосредственно на mmap (без копирования), гарантируя, что mmap не будет закрыт до завершения использования (через ref‑count). Для VLog/unified‑mmap уже есть копирование, но можно оптимизировать через `VLogView`. Добавить тест на аллокации в `GetExisting`.

### DEF‑D8 (НОВЫЙ) — Аллокации в `Put` (2 allocs/op вместо 1)

**Файлы:** `internal/engine/memtable/arena.go`, `internal/engine/lsm.go`

**Проблема:**  
`BenchmarkPutSmallValue` показывает 2 allocs/op. Причина: лишнее копирование значения при вставке в MemTable (`inlineValue` vs `storedValue`).

**Последствия:**  
- Дополнительная нагрузка на GC, снижение пропускной способности записи.

**Статус:** ❌ Не исправлено.

**Промпт для исправления:**  
> В `PutWithTS` передавать `storedValue` напрямую в `memTable.Put`, избегая промежуточного буфера. Использовать арену для хранения значения без дублирования. Добавить тест: `-benchmem` должен показывать 1 alloc/op.

### DEF‑D9 (НОВЫЙ) — Аллокации в `Scan` (30 allocs/op)

## Часть 2. СИСТЕМА ПРОМПТОВ ДЛЯ ИСПРАВЛЕНИЯ

Для каждого дефекта (или группы связанных) ниже приведён промпт, который можно скормить агенту (Source Craft или другому). Промпты следуют в порядке приоритета:

### Промпт 1: Исправление DEF‑A2 (восстановление таймстампов) и DEF‑A1 (unsafeToString)

```text
Исправить два критических дефекта:
1. Восстановление таймстампов после рестарта (DEF-A2). Реализовать сбор maxTS в recoverFromWAL и установку LastTS.
2. unsafeToString в lastCommitCache (DEF-A1). Заменить на копирование ключа или хеш.

Критерии: go test -race проходит, тест на восстановление таймстампов успешен.
```

### Промпт 2: Исправление DEF‑A3 (endianness) и DEF‑B4 (memcpyWordAligned)

```text
Исправить:
1. Unified mmap: привести запись и чтение к единому endianness (BigEndian).
2. Убрать невыровненный доступ в memcpyWordAligned, заменить на copy().

Критерии: тесты на ARM64 (или симуляция) проходят, нет SIGBUS.
```

### Промпт 3: Исправление DEF‑A5 (Manifest recovery), DEF‑A6 (fsync в Strict Sync), DEF‑A7 (дупликация батчей)

```text
1. Manifest.recover: различать повреждение середины и хвоста.
2. В Strict Sync дожидаться fsync в Flush.
3. Восстановление OpBatch: фильтровать операции по шарду.

Критерии: crash-тесты проходят, TestWAL_Corruption_Debug проходит.
```

### Промпт 4: Исправление MVCC-дефектов (DEF‑C1..C6)

```text
1. SSTable.Lookup: выбирать последнюю версию для снапшота.
2. MVCCIterator: сбрасывать hasTombstone при живой версии.
3. Транзакции: RegisterSnapshot при Begin.
4. UnregisterSnapshot: reference-counting для минимума.
5. Компакшн: использовать актуальный минимум.
6. mergeIterator: дедуплицировать по full key.

Критерии: все тесты на MVCC и снапшоты проходят.
```

### Промпт 5: Исправление DEF‑B5, DEF‑B6 (e.levels, decodeMVCCKey)

```text
1. Аудит e.levels: все чтения под RLock, копирование слайсов.
2. В SSTableIterator копировать ключи при выдаче наружу.

Критерии: -race чист, нет use-after-free.
```

### Промпт 6: Исправление DEF‑D1..D5 (производительность)

```text
1. Переименовать Next() в Current() или сделать инкремент.
2. maybeCompact: убрать горутину под Lock.
3. lastCommitCache: ограничить размер (LRU).
4. GetLatestInfo: копировать levels под коротким RLock.
5. readBlockFromFile: использовать uint64 для totalSize.

Критерии: бенчмарки показывают улучшение, нет contention.
```

### Промпт 7: Исправление DEF‑D6 (масштабирование shard-per-core)

```text
Комплексное улучшение shard-per-core:
- Улучшить хеширование (xxHash64).
- Устранить глобальные блокировки в Get (копировать указатели, отпускать).
- В бенчмарках использовать много ключей.

Критерии: на 8 ядрах QPS не падает, а растёт (хотя бы 1.5x от 1 ядра).
```

### Промпт 8: Исправление DEF‑D7, D8, D9 (аллокации)

```text
1. decodeStoredValue: для SSTable возвращать срез на mmap без копирования (с ref-count).
2. PutWithTS: убрать лишнее копирование, добиться 1 alloc/op.
3. Scan: оптимизировать mergeIterator, уменьшить allocs до ≤5.

Критерии: -benchmem показывает 0 B/op для Get, 1 alloc/op для Put, ≤5 для Scan.
```
