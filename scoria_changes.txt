+## 7. ДОПОЛНИТЕЛЬНЫЕ НАБЛЮДЕНИЯ
+
+### 7.1. Проблема в `GetLatestInfo()`
+
+В [`lsm.go:430-460`](internal/engine/lsm.go:430) метод `GetLatestInfo()` для поиска в SSTable использует **полный итератор** вместо `Lookup()`:
+
+```go
+iter, err := sst.NewIterator()
+// ... полный проход всех блоков
+for iter.Next() {
+    mvccKey := iter.Key()
+    if bytes.Equal(mvccKey.Key, key) {
+        // ...
+    }
+}
+```
+
+Это O(N) на каждый SSTable. Должно быть O(log N) через `Lookup()` с правильной обработкой версий.
+
+### 7.2. Проблема с `encodeEntry()` — аллокация
+
+В [`writer.go:233-242`](internal/engine/sstable/writer.go:233) `encodeEntry()` делает `make([]byte)` на каждую запись. В горячем пути флаша это приемлемо (флаш не горячий), но можно оптимизировать через `bytes.Buffer` или pre-allocated буфер.
+
+### 7.3. Bloom filter — фиксированный размер
+
+В [`bloom.go:41`](internal/engine/sstable/bloom.go:41) размер Bloom filter фиксирован (1024 байта). Для 100K ключей это даёт высокий false positive rate. Нужно вычислять размер динамически на основе `NumKeys` из footer.
+
+### 7.4. `k` (число хеш-функций) не оптимально
+
+В [`bloom.go:44`](internal/engine/sstable/bloom.go:44) `k = uint32(bitsPerKey)` (10). Оптимальное `k = (m/n) * ln(2)`. При фиксированном m=8192 бит и n=100K ключей, оптимальное k ≈ 0.057 — фактически 1 хеш-функция. Текущее k=10 даёт ~100% false positive rate.

+## Task 1: Key Correctness Analysis
+
+### Code Trace
+
+**encodeMVCCKey** (`internal/engine/sstable/encoding.go:26-33`):
+```
+Format: [2-byte keyLen LE][key bytes][8-byte timestamp LE]
+```
+- `keyLen` = `uint16(len(key.Key))` — 2 bytes, little-endian
+- `key` = raw key bytes
+- `timestamp` = `key.Timestamp` — 8 bytes, little-endian
+- Total: `2 + kl + 8` bytes
+
+**decodeMVCCKey** (`internal/engine/sstable/encoding.go:36-50`):
+```
+Reads: [2-byte keyLen LE][key bytes][8-byte timestamp LE]
+```
+- Reads `keyLen` from first 2 bytes
+- Reads `userKey` as `data[2 : 2+kl]`
+- Reads `timestamp` as `binary.LittleEndian.Uint64(data[2+kl:])`
+
+**Symmetry**: `decodeMVCCKey(encodeMVCCKey(key))` produces a `MVCCKey` with identical `Key` bytes and `Timestamp`. The decoded `Key` is a slice of the encoded buffer, not the original, but content is identical. **Symmetric ✓**
+
+**Index Entry** (`internal/engine/sstable/writer.go:129`):
+- `flushBlock` stores `w.blockStartKey` — the **encoded MVCCKey** of the first key in the block
+- `blockStartKey` is set in `Append` (line 107) as `keyBytes = encodeMVCCKey(key)`
+- This is a fresh `make([]byte, ...)` allocation, no aliasing issues
+
+**Binary Search in Lookup** (`internal/engine/sstable/reader.go:539-545`):
+- `sort.Search` finds first index where `idxKey.Key > userKey`
+- `idxKey` is obtained by `decodeMVCCKey(r.indexEntries[i].key)` — decoding the stored encoded key
+- `idxKey.Key` is the user key part (without timestamp)
+- Comparison: `keys.CompareKeys(idxKey.Key, userKey) > 0`
+- Then `blockIdx--` to get the block where `firstKey <= userKey`
+- **Correct ✓**
+
+**Benchmark Keys** (`internal/engine/sstable/benchmark_test.go:42`):
+- Write: `mvcc.NewMVCCKey([]byte{byte(i >> 8), byte(i)}, uint64(i+1))`
+- Read: `mvcc.NewMVCCKey([]byte{byte(idx >> 8), byte(idx)}, uint64(idx+1))`
+- Same format, same timestamp. **Correct ✓**
+
+### Conclusion
+
+The encode/decode, index storage, binary search, and benchmark key format are all **correct**. The `BenchmarkSSTableRead` failure is likely caused by one of:
+
+1. **A very subtle edge case** in the mmap read path (bounds checking off-by-one)
+2. **A race condition** in concurrent access
+3. **An environmental issue** (test setup, file system)
+
+**Recommended action**: Run the benchmark with `-race` and `-v` to capture the exact failure, then fix based on the actual error.

+## Task 2: 0 Allocs in Lookup (BLOCKER-03)
+
+### Current State
+
+In `Lookup` (`internal/engine/sstable/reader.go:598-601`):
+```go
+// Copy value before returning (blockData may be from mmap or pool)
+val := make([]byte, len(entryVal))
+copy(val, entryVal)
+return val, true
+```
+
+This performs **1 allocation per Lookup**. With mmap, `blockData` is a slice of the mmap region, so `entryVal` is also an mmap slice. The copy is unnecessary for mmap users.
+
+### Fix 1: Return mmap slice directly from Lookup
+
+**File**: `internal/engine/sstable/reader.go`
+
+Change the value return in `Lookup` from:
+```go
+val := make([]byte, len(entryVal))
+copy(val, entryVal)
+return val, true
+```
+To:
+```go
+return entryVal, true
+```
+
+**Contract**: Document that the returned value is valid only until `Close()`.
+
+### Fix 2: Copy SSTable values in decodeStoredValue
+
+**File**: `internal/engine/lsm.go`
+
+Currently `decodeStoredValue` (line 639-663) returns `stored` directly for non-VLog, non-unified-mmap values:
+```go
+return stored, nil
+```
+
+When the value comes from an SSTable, `stored` is a slice of the mmap region. It must be copied because the caller may use it after the SSTable Reader is closed.
+
+Change to:
+```go
+// SSTable value — slice of mmap region, must copy
+val := make([]byte, len(stored))
+copy(val, stored)
+return val, nil
+```
+
+### Fix 3: Fix SSTableIterator value copying
+
+**File**: `internal/engine/sstable/iterator.go`
+
+The iterator already copies values (line 98-99):
+```go
+val := make([]byte, len(entryVal))
+copy(val, entryVal)
+it.val = val
+```
+
+This is **correct** — iterator values must be stable across block transitions. No change needed here.
+
+### Fix 4: Add zero-allocation contract to Lookup
+
+**File**: `internal/engine/sstable/reader.go`
+
+Add documentation:
+```go
+// Lookup returns a value slice that points directly to the mmap region.
+// The value is valid only until the Reader is closed.
+// The caller MUST copy the value if it needs to persist beyond the lifetime
+// of the Reader.
+//
+// This is a zero-allocation optimization. The returned slice is a reference
+// to the mmap region, not a copy. Use with caution.
+```
